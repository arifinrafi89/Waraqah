# Refactor Plans

Generated by an architecture audit on 2026-09-22, against commit `02b95e1`
(branch `frontend-setup`). Each plan is self-contained: an executor with no
other context should be able to read one file and carry it out.

**Not the same thing as `docs/plans/`.** Those are feature-build specs (cart,
checkout, orders, search, ai-chat — things the app does not do yet). These are
structural changes to code that already exists. No plan here adds a user-facing
feature.

Each executor: read the plan fully before starting, honor its STOP conditions,
and update your row below when done.

Published as a spec: **[#28](https://github.com/arifinrafi89/Waraqah/issues/28)**
(`ready-for-agent`). The issue is the why, the user-visible contract and the
testing approach for all four plans; these files are the step-by-step. One test
seam applies across the set — the router-level widget test, with repository
providers overridden where write-through or failure needs to be observed. No
plan here adds a `ProviderContainer` unit test.

## Dependency notes

- **002 depends on nothing** and touches no file that 001 touches
  (`cart`, `checkout`, `main.dart`, `CLAUDE.md` versus `home`, `p2p`,
  `book_bites`, `profile`, `orders`). It can run first, last, or on a parallel
  branch. It is the smallest plan here and a reasonable warm-up.
- **003 requires 001** because it edits the providers 001 relocates. Running
  003 first would mean editing those files twice and resolving a conflict.
- **004 requires 003** specifically so every call site is edited once. 003
  changes the *shape* of the write path (free function → notifier method); 004
  changes its *timing* (sync → async). Reversing the order means touching the
  same seven call sites twice.
- 001 → 003 → 004 is one continuous line of work on the same subsystem. If
  only part of the set gets done, stopping after 003 leaves the codebase in a
  coherent state; stopping midway through 004 does not.

## What the audit found, in one line each

1. `features/home` owned the domain models of three other features; 19 imports
   reached into it, 7 of them into its presentation layer. → plan 001
2. Repository providers were declared inside `presentation/controllers/`. → plan 001
3. Repository interfaces are synchronous, so the Supabase swap ADR-0001
   promises is not a data-layer swap. → plan 004
4. Writes bypass the repository entirely; there is no insert seam, and cart
   mutations are free functions taking a `WidgetRef`. → plan 003
5. The delivery fee is defined twice and `CartItemTotal` lives in the wrong
   feature. → plan 002
6. `themeMode: ThemeMode.light` is a dead argument, and `CLAUDE.md` documents
   theme behavior the app does not have. → plan 002

## Findings considered and rejected

- **Duplicated filter/sort provider pairs on Home and Catalog**
  (`homeBookFilterProvider` / `catalogBookFilterProvider`, and the two nearly
  identical `filtered*BooksProvider`s): not duplication to fix. Each screen
  keeping its own independent filter and sort selection is intended behavior;
  sharing the providers would make changing the sort on Catalog silently change
  it on Home.
- **Dummy repositories exposing their backing lists**: already safe. Every
  `get*` returns `List.unmodifiable(...)`, and no caller sorts or mutates in
  place — `sortBooks` copies with `[...books]` and the p2p filter sorts a
  `.toList()` copy.
- **`lib/core/data/dummy_book_repository.dart` living in `core`**: correct as
  is. `Book` is shared by six features, and ADR-0001 scopes the dummy data as a
  deliberate throwaway stand-in for the Supabase `books` table.

## Known gaps not planned here

Real, but judged not worth a plan yet — recorded so they are not re-audited:

- **`home_page.dart` is 641 lines** and its private `_BiteCard` and `_P2pCard`
  widgets duplicate parts of `book_bites/.../post_card.dart` and
  `p2p/.../p2p_grid_card.dart`. The home variants are visually different from
  the feed versions, so deduplicating them is layout work with real regression
  risk and little structural payoff. Worth doing when one of those cards next
  needs a design change, not before.
- **No auth state exists.** `currentProfileId = 'profile-1'` is a constant, and
  `ARCHITECTURE.md` §8 promises route guards that do not exist. Plan 001
  consolidates that constant into `lib/core/providers/profile_providers.dart`
  as the single seam to replace, which is as far as it is worth going before
  Supabase Auth is actually configured.
- **A Supabase spike.** Wiring exactly one repository end to end against a real
  Supabase project would validate or kill plan 004's premise with evidence
  instead of argument. It needs a Supabase project to exist first, which it
  does not.
- **`ai_assistant` docs are ahead of code.** `CONTEXT.md` defines `ChatMessage`
  and `VendorQuote`, and `docs/plans/05-ai-chat.md` is written, but no
  `lib/features/ai_assistant/` exists and `/ai-chat` is still a
  `PlaceholderPage`. That is a feature build, not a refactor — it belongs in
  `docs/plans/`.

## What was not audited

This audit was scoped to architecture at the user's request. Untouched:
security, performance, accessibility, dependency currency, UI correctness, and
the platform directories (`android/`, `ios/`, `macos/`, `web/`, `linux/`,
`windows/`).

Baseline at audit time: `flutter analyze` → `No issues found!`,
`flutter test` → 56 passing.
